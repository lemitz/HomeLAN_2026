# 🏛️ Архитектура и сетевой протокол (Technical Architecture)

**HomeLAN Messenger v2.3 FINAL (Release Candidate)**

---

## 1. Обзор системы
* **Назначение:** Полностью приватный self-hosted мессенджер для домашней локальной сети (LAN) без выхода в интернет и облачных зависимостей.
* **Масштаб:** 2 пользователя, до 4 устройств (например, 2 стационарных ПК на Windows + 2 смартфона на Android).
* **Сервер:** Микрокомпьютер (Orange Pi Zero 3 / Raspberry Pi / x86_64 Linux или Windows), 2GB RAM. Язык — Go 1.21+, база данных — SQLite + SQLCipher в режиме WAL.
* **Клиенты:** Кроссплатформенное приложение на Flutter (3.16+), база данных — SQLite (`drift` + `sqlcipher`), криптографическое ядро — `flutter_sodium` (libsodium).

---

## 2. Спецификация сетевых протоколов

### 2.1. Транспортный уровень
* **WebSocket (`/ws`):** Использование сокетов для передачи сигнальных событий, текстовых сообщений, статусов прочтения (ACK/READ), удалений (Tombstones) и поддержания соединения (Ping/Pong).
* **HTTP/REST:** Использование HTTP-эндпоинтов для загрузки/скачивания файлов (с поддержкой Range-запросов и потоковой передачи), авторизации и первичного обмена ключами.

### 2.2. Таблица HTTP-эндпоинтов
| Метод  | Эндпоинт                     | Описание |
|--------|------------------------------|----------|
| `GET`  | `/health`                    | Проверка работоспособности сервера и получение `server_time` |
| `GET`  | `/api/time`                  | Получение точного серверного времени (Unix Timestamp) |
| `POST` | `/api/register`              | Регистрация пользователя и первого устройства |
| `POST` | `/api/login`                 | Авторизация устройства (с поддержкой проверки *Duress Password*) |
| `GET`  | `/api/user/{id}`             | Получение публичного ключа и информации о пользователе |
| `GET`  | `/api/partner`               | Получение информации об автоматическом собеседнике в LAN |
| `POST` | `/api/files/upload`          | Загрузка зашифрованного файла (поток с контролем RAM до 32 МБ) |
| `GET`  | `/api/files/{id}`            | Скачивание файла с поддержкой заголовка `Range` |
| `POST` | `/api/devices/link/create`   | Генерация одноразового кода для привязки нового устройства |
| `POST` | `/api/devices/link/complete` | Завершение привязки устройства |
| `GET`  | `/api/devices`               | Список привязанных устройств пользователя |
| `POST` | `/api/devices/revoke`        | Отзыв (компрометация) устройства |
| `POST` | `/api/panic`                 | Ручной триггер экстренного затирания данных (*Panic Wipe*) |

## 3. WebSocket протокол и форматы данных

Все сообщения в канале `/ws` имеют базовую обертку JSON:
```json
{
  "type": "<имя_события>",
  "data": { ... }
}
```

### 3.1. Отправка и получение сообщений (`send_message` / `new_message`)
Отправка сообщения клиентом:
```json
{
  "type": "send_message",
  "data": {
    "recipient_id": 2,
    "encrypted_content": "<base64_blob>",
    "content_type": "encrypted",
    "file_id": "file_8A7B9C...",
    "expires_at": 1735689600
  }
}
```
Рассылка сервером (`new_message`) получателю и остальным устройствам отправителя:
```json
{
  "type": "new_message",
  "data": {
    "seq_id": 142,
    "sender_id": 1,
    "recipient_id": 2,
    "encrypted_content": "<base64_blob>",
    "content_type": "encrypted",
    "file_id": null,
    "created_at": 1704067200,
    "expires_at": 0
  }
}
```
> **ВАЖНО:** Генерация `seq_id` на сервере является строго монотонной и защищена мьютексом (`db.mu.Lock()`), исключающим гонки потоков при параллельной отправке.

### 3.2. Синхронизация истории (`sync` / `sync_response`)
Для обеспечения работы в офлайн-режиме каждое устройство хранит свой курсор `last_seq_id`. При подключении устройство отправляет запрос синхронизации:
```json
{
  "type": "sync",
  "data": {
    "since_seq_id": 140,
    "before_seq_id": 0,
    "limit": 50
  }
}
```
* **Прямая синхронизация (`before_seq_id = 0`):** Сервер возвращает все сообщения с `seq_id > since_seq_id` и обновляет курсор устройства в таблице `sync_cursors`.
* **Обратная пагинация (`before_seq_id > 0`):** Сервер возвращает историю до указанного номера, **не перезаписывая** курсор синхронизации.

## 4. Криптографический стек (E2E-Шифрование)

```
[ Отправитель (Alice) ]                                  [ Получатель (Bob) ]
 ├── Private Key (X25519)                                 ├── Private Key (X25519)
 └── Public Key (Bob)                                     └── Public Key (Alice)
       │                                                        │
       ▼                                                        ▼
  Shared Secret (ECDH X25519)                             Shared Secret (ECDH X25519)
       │                                                        │
       ▼                                                        ▼
  Симметричный ключ                                       Симметричный ключ
       │                                                        │
       ├──► XChaCha20-Poly1305 (Шифрование) ──[LAN]──► XChaCha20-Poly1305 (Дешифровка)
```

1. **Асимметричные ключи:** Каждый пользователь имеет долгосрочную пару ключей **X25519** (256 бит). Публичные ключи хранятся на сервере и сверяются по отпечаткам (Fingerprints).
2. **Алгоритм шифрования:** Сообщения и метаданные файлов шифруются аутентифицированным шифром **XChaCha20-Poly1305** с 192-битным случайным `nonce`.
3. **Хранение на устройстве:** Приватные ключи на клиентах защищены через хранилища платформы (Android Keystore / Windows DPAPI / `SharedPreferences` + `sqlcipher`).

## 5. Алгоритм синхронизации времени (Time Delta Sync)

Микрокомпьютеры (Orange Pi Zero 3) часто не имеют батарейки RTC и без подключения к интернету (NTP) могут испытывать дрифт часов. Кроме того, часы на смартфонах пользователей могут расходиться.

### Решение в HomeLAN v2.3:
1. При каждом успешном HTTP-запросе (`/health`, `/api/login`, `/api/time`) или WebSocket-сообщении сервер передает свой текущий `server_time` (Unix Timestamp).
2. Клиентский сервис `TimeService` вычисляет смещение:
   $$\Delta t = \text{server\_time} - \text{local\_time}$$
3. Любое создаваемое на клиенте сообщение или запрос использует откалиброванное время:
   $$t_{\text{msg}} = \text{local\_time} + \Delta t$$
4. При расхождении более 6 часов или при каждом новом WebSocket-подключении дельта автоматически пересчитывается.

## 6. Защита от OOM при файловом стриминге

На устройствах с 2 ГБ RAM критически важно избегать буферизации больших файлов в память:
1. **Ограничение тела запроса:** Обработчик `/api/files/upload` использует `http.MaxBytesReader(w, r.Body, maxFileSize)`.
2. **Контроль оперативной памяти:** Вызов `r.ParseMultipartForm(32 << 20)` гарантирует, что в RAM осядет не более **32 МБ**, а остальной поток сбрасывается во временные дисковые файлы Go.
3. **Прямое копирование:** Данные записываются в хранилище через `io.Copy(dst, io.LimitReader(file, maxFileSize))` без промежуточного чтения всего массива в память (`ReadAll`).
4. **Проверка дискового пространства:** Перед записью выполняется системный вызов `utils.HasEnoughSpace`, требующий наличия свободного места с запасом в 100 МБ.
