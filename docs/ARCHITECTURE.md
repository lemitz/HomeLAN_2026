# Архитектура HomeLAN Messenger (протокол v2)

## 1. Обзор

| | |
|---|---|
| Назначение | Приватный мессенджер для домашней сети, без интернета и облаков |
| Масштаб | 2 пользователя, по умолчанию до 3 устройств у каждого (`max_devices_per_user`) |
| Сервер | Go 1.22+, SQLite + SQLCipher, ключ БД на USB-флешке. Orange Pi Zero 3 / любой Linux / Windows |
| Клиенты | Flutter: Android и Windows |

**Сервер — источник правды.** Он хранит всю переписку в зашифрованном (E2E) виде.
Клиент держит кеш шифротекстов и курсор синхронизации; кеш можно удалить в любой
момент — история восстановится с сервера. Расшифрованный текст существует только
в памяти клиента.

## 2. Ключи и идентичность

* У каждого **пользователя** один identity-ключ X25519. Он создаётся при
  регистрации и хранится в защищённом хранилище ОС (Android Keystore /
  Windows DPAPI через `flutter_secure_storage`).
* Публичный ключ пользователя хранится на сервере и **не меняется** входом.
* Новое устройство получает identity-ключ только через привязку (раздел 5).
  Вход по паролю разрешён лишь с уже привязанного устройства.
* При каждом входе клиент сверяет свой ключ с ключом аккаунта на сервере —
  если сервер подменён, вход останавливается.
* Ключ собеседника закрепляется при первом получении (TOFU). Если сервер
  пришлёт другой ключ, отправка блокируется до ручной сверки отпечатка
  (safety number, 60 цифр, одинаковы у обоих собеседников).

## 3. Шифрование

**Сообщения**

```
shared   = X25519(мой identity, его identity)
key      = HKDF-SHA256(shared, salt="homelan-v2-salt", info="homelan/v2/msg/<min id>/<max id>")
aad      = "homelan/v2|<sender>|<recipient>|<content_type>|<client_id>"
blob     = 0x02 | nonce(24) | XChaCha20-Poly1305(key, nonce, plaintext, aad) | mac(16)
```

AAD не даёт серверу выдать сообщение за ответ собеседника (отражение), сменить
тип (текст ↔ файл) или незаметно повторить сообщение (client_id уникален).
Сервер отвергает любое содержимое, у которого первый байт не `0x02`.

**Файлы** шифруются потоково, каждый своим случайным 32-байтовым ключом
(XChaCha20-Poly1305 блоками по 256 КБ, номер блока и флаг последнего блока в AAD).
Ключ файла, имя, размер и MIME лежат в зашифрованном сообщении (`content_type`
`image`/`file`). Сервер видит только размер зашифрованного файла.

## 4. Сессии и HTTP API

Токен — 32 случайных байта (hex). На сервере хранится только SHA-256.
Передаётся **только** в заголовке `Authorization: Bearer <token>` (в том числе для
WebSocket). Срок жизни скользящий (`session_days`, по умолчанию 90).
Отзыв устройства мгновенно отзывает все его сессии и рвёт WebSocket.

Ошибки: `{"error": "<код>", "message": "<текст>"}`.

| Метод | Путь | Сессия | Назначение |
|---|---|:---:|---|
| GET | `/health`, `/api/time` | — | статус, `server_time`, `protocol` |
| POST | `/api/register` | — | пользователь + первое устройство + публичный ключ |
| POST | `/api/login` | — | вход с привязанного устройства |
| POST | `/api/logout` | да | отзыв текущей сессии |
| GET | `/api/session` | да | проверка сессии, данные пользователя и собеседника |
| GET | `/api/partner` | да | собеседник и его публичный ключ |
| GET | `/api/users/{id}` | да | только свой профиль или собеседника |
| GET | `/api/devices` | да | активные устройства пользователя |
| POST | `/api/devices/revoke` | да | отзыв устройства |
| POST | `/api/devices/link/create` | да | код привязки для конкретного нового устройства |
| POST | `/api/devices/link/complete` | — | завершение привязки (код одноразовый) |
| POST | `/api/files/upload` | да | потоковая загрузка зашифрованного файла |
| GET | `/api/files/{id}` | да | скачивание (Range), только загрузившему и получателю |
| POST | `/api/panic` | админ | вайп; требует пароль и `"confirm":"DESTROY_ALL_DATA"` |
| GET | `/ws` | да | WebSocket |

Логин, регистрация, panic и завершение привязки ограничены по частоте
(блокировка IP на 15 минут после серии неудач).

## 5. Привязка устройства (2-QR + текст)

```
НОВОЕ устройство                          ОСНОВНОЕ устройство
1. эфемерный ключ E, device_id
2. QR#1 / текст "HL1:..." ─────────────►  3. сканирует, показывает код сверки
   (код сверки 6 цифр)                     4. пользователь сверяет коды
                                           5. POST link/create {device_id} → код
                                           6. identity шифруется на E
7. сканирует / вставляет  ◄─────────────   QR#2 / текст "HL2:..."
8. расшифровывает identity
9. POST link/complete {код, device_id}
10. проверяет: identity совпадает с ключом аккаунта
```

Код привязки: 10 символов (~49 бит), живёт 5 минут, одноразовый и привязан к
`device_id` нового устройства. Сервер не видит identity-ключ. QR#2 бесполезен
для любого, у кого нет эфемерного ключа нового устройства.

## 6. WebSocket (протокол v2)

Обёртка: `{"type": "...", "data": {...}}`.

Клиент → сервер:

| type | data |
|---|---|
| `send_message` | `client_id`, `recipient_id`, `content_type` (`text`/`image`/`file`), `encrypted_content` (base64), `file_id`?, `expires_at`? |
| `sync` | `since` (курсор change_seq), `limit` |
| `history` | `before_seq`, `limit` |
| `ack` | `seq_id` — доставлено (только получатель) |
| `read` | `up_to_seq` — прочитано всё до seq включительно |
| `delete` | `seq_id` (только отправитель) |
| `typing` | `recipient_id` |
| `ping` / `time_sync` | — |

Сервер → клиент: `message` (полное состояние сообщения после любого изменения),
`message_sent` (`client_id`, `seq_id`), `send_failed` (`client_id`, `code`),
`sync_response` (`messages`, `cursor`, `has_more`), `history_response`,
`typing`, `pong`, `error`.

### Синхронизация

У сообщения два номера: `seq_id` (постоянный id) и `change_seq` (монотонный номер
последнего изменения: создание, доставка, прочтение, удаление). Удаление
превращает сообщение в tombstone (содержимое стирается, `is_deleted=true`) с
новым `change_seq`. Клиент после каждого подключения запрашивает `sync` с
сохранённым курсором и получает **все** изменения, включая удаления и статусы,
постранично (`has_more`).

### Доставка без потерь

Исходящее сообщение сначала сохраняется в локальный outbox с `client_id`
(UUID), затем отправляется. После переподключения outbox отправляется повторно;
сервер дедуплицирует по `(sender_id, client_id)`. Если клиент не успевает
читать, сервер закрывает соединение — при переподключении клиент
досинхронизируется по курсору.

## 7. Клиент

* Экран блокировки (Android) и экран «сервер недоступен» (Windows) рисуются
  поверх навигатора — открытые экраны и их состояние сохраняются.
* Биометрия / PIN устройства, fail-closed. Системные пикеры и камера не
  блокируют приложение.
* Android: `FLAG_SECURE`, `allowBackup=false`. Windows: окно исключено из
  захвата экрана, один экземпляр.
* Расшифрованные файлы — во временной папке, очищается при старте.
* Сетевая ошибка никогда не разлогинивает и ничего не стирает.

## 8. Время

Сервер присылает `server_time` в ответах; клиент хранит поправку и использует её
для отметок времени (Orange Pi без RTC может стартовать с неверными часами —
Dead Man's Switch при годе < 2024 не срабатывает).
