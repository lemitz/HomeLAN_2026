# 🛡️ Модель угроз и политика безопасности (Threat Model)

**HomeLAN Messenger v0.5.0 Release Candidate**

В этом документе описывается модель нарушителя, реализованные защитные механизмы, сценарии экстренного уничтожения данных, а также документированные и принятые ограничения системы.

---

## 1. Сводная матрица угроз и принятых рисков

| Угроза / Вектор атаки | Реализованная защита | Текущий Статус / Ограничения |
|---|---|---|
| **Физический захват сервера** | Аппаратный USB Master Key + экстренный вайп при извлечении | ✅ Защищено. Данные уничтожаются мгновенно при извлечении USB-накопителя. |
| **Атака «Человек посередине» (MITM) в LAN** | Сквозное шифрование (E2E) ChaCha20-Poly1305 | ⚠️ **Частично защищено**. Хотя содержимое сообщений и файлов зашифровано (E2E), транспортные данные (пароль при входе, метаданные, сессионные токены) передаются по открытому HTTP/WebSocket. В случае скомпрометированной LAN (например, взломанный Wi-Fi роутер), злоумышленник может перехватить сессию. |
| **Компрометация одного из устройств** | Механизм отзыва (`Revoke`) + ротация сессионных токенов | ✅ Защищено. Администратор может отозвать устройство, принудительно отключив его сессию и WebSocket соединение. |
| **Принуждение к разблокировке (Duress)** | Пароль принуждения (`duress_password`), запускающий скрытый вайп | ✅ Защищено. Ввод этого пароля на экране входа незаметно запускает фоновое стирание. |
| **Захват оставленного без присмотра сервера** | *Dead Man's Switch* (автовайп при отсутствии админа > 30 дней) | ✅ Защищено. Процесс мониторинга автоматически уничтожает БД при превышении лимита времени. |
| **Форензика диска / SD-карты сервера** | SQLCipher (AES-256) + затирание 4 КБ заголовка случайными байтами | ✅ Защищено. Уничтожение заголовка делает SQLCipher БД полностью нечитаемой. |
| **Форензика диска / памяти клиента** | Хранение сессионных токенов и ключей в secure storage | ⚠️ **Частично защищено**. Приватные X25519 ключи и сессионные токены перенесены в защищенное хранилище (Android Keystore / Windows DPAPI). Однако, сама локальная SQLite база данных клиента не шифруется — метаданные чата (время, списки диалогов, имена файлов) хранятся в открытом виде. |
| **Рассинхронизация часов в LAN** | Алгоритм *Time Delta Sync* (работает без NTP и батарейки RTC) | ✅ Защищено. |

## 2. Архитектура экстренного уничтожения данных (Panic / Duress Wipe)

Сервер HomeLAN рассчитан на сценарии, когда физическое оборудование (Orange Pi Zero 3 или диск) может попасть в чужие руки. В системе реализован модуль `internal/panic/panic.go`, выполняющий затирание криптографических заголовков и файлов.

```
      [ Триггеры ]
 ├── Выдернута USB-флешка (USB Master Key)
 ├── Введен пароль принуждения (Duress Password)  ──► [ Модуль PanicHandler ]
 ├── Сработал таймер Dead Man's Switch                           │
 └── POST /api/panic (API запрос)                                │
                                                                 ▼
                                                  1. Закрытие соединения с БД (снятие локов)
                                                  2. Удаление временных WAL и SHM файлов
                                                  3. Перезапись первых 4 КБ БД (/dev/urandom)
                                                  4. Затирание и удаление всех файлов в хранилище
                                                  5. Системный вызов syscall.Sync() (сброс буферов)
                                                  6. Завершение процесса (os.Exit)
```

### 2.1. Ограничения затирания на Flash-памяти (Wear Leveling)
При перезаписи файлов на современных Flash-накопителях (SSD, SD-карты, eMMC), микроконтроллер накопителя использует алгоритм **выравнивания износа (Wear Leveling)**. 

Это означает, что при перезаписи первых 4 КБ файла базы данных, контроллер может записать новые случайные байты в другую физическую ячейку, а старую пометить как "неиспользуемую" для последующей очистки сборщиком мусора. В этот промежуток времени физическая ячейка с оригинальными данными всё ещё может быть считана с помощью специализированного лабораторного оборудования (форензика чипов).

**Выводы и рекомендации:**
1. Разработчики не гарантируют 100% физическое затирание секторов на полупроводниковых дисках силами пользовательского приложения.
2. Для абсолютной защиты от лабораторного анализа аппаратной памяти сервера настоятельно рекомендуется использовать полнодисковое шифрование на уровне операционной системы (например, **dm-crypt / LUKS** в Linux) в сочетании с встроенным механизмом вайпа.

## 3. Сценарии активации защиты

### 3.1. Аппаратный ключ (USB Master Key)
* Сервер запускает фоновую горутину, которая проверяет наличие файла `homelan.key` на подключенных USB-накопителях каждые 1 секунду.
* Для защиты от случайных скачков напряжения или кратковременных сбоев шины питания (glitch), система выполняет 3 быстрых повторных опроса (через каждые 50 мс) перед активацией экстренного удаления.
* Если диск действительно извлечен, сервер немедленно вызывает `Trigger("USB_KEY_GONE_CONFIRMED")`.

### 3.2. Пароль принуждения (Duress Password)
* В конфигурации `config.yaml` задается параметр `duress_password`.
* Если пользователь находится под давлением и вводит этот пароль на экране входа, эндпоинт `/api/login` немедленно возвращает HTTP-статус `401 Unauthorized`.
* В фоновом потоке через 500 миллисекунд активируется процедура полного уничтожения данных.

### 3.3. Переключатель мертвеца (Dead Man's Switch)
* Сервер раз в час проверяет время последней активности администратора.
* Если с момента последней активности прошло более `timeout_days` (по умолчанию 30 дней), запускается автовайп.
* Имеется встроенная защита от сброса системного времени на Orange Pi Zero 3 без батарейки RTC (проверка, что текущий год >= 2024 перед запуском логики).

## 4. Криптографические ограничения

1. **Отсутствие Perfect Forward Secrecy (PFS):**
   В текущей версии протокола сквозного шифрования (E2E) используются статические ключи **X25519** для деривации общего секрета. Это означает, что если злоумышленник скомпрометирует (украдет) приватный статический ключ одного из пользователей, он сможет расшифровать всю историю переписки (включая все перехваченные ранее зашифрованные сообщения). perfect forward secrecy в текущей версии **не обеспечивается**.

2. **ChaCha20-Poly1305 vs XChaCha20-Poly1305:**
   В отличие от заявленного ранее алгоритма XChaCha20-Poly1305 (с 24-байтовым случайным nonce), код использует стандартный **ChaCha20-Poly1305** с 12-байтовым nonce. При этом nonce генерируется случайным образом при каждом шифровании. Во избежание риска повторного использования пары (key, nonce), разработчики рекомендуют обновлять ключевую пару пользователей раз в месяц.
