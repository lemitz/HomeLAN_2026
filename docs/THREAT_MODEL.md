# 🛡️ Модель угроз и политика безопасности (Threat Model)

**HomeLAN Messenger v0.5.0 Release Candidate**

В этом документе описывается модель нарушителя, реализованные защитные механизмы, сценарии экстренного уничтожения данных, а также документированные и принятые ограничения системы.

**Целевое окружение:** закрытая домашняя Wi-Fi/LAN сеть с двумя доверенными пользователями и без посторонних устройств. Защита от активного атакующего внутри сети (MITM, подмена сервера) сознательно **не является целью** текущей версии — см. раздел 4.

---

## 1. Сводная матрица угроз и принятых рисков

| Угроза / Вектор атаки | Реализованная защита | Текущий Статус / Ограничения |
|---|---|---|
| **Физический захват сервера** | Аппаратный USB Master Key + экстренный вайп при извлечении | ✅ Защищено. Данные уничтожаются при извлечении USB-накопителя (полная перезапись БД, см. раздел 2). |
| **Атака «Человек посередине» (MITM) в LAN** | Сквозное шифрование (E2E) ChaCha20-Poly1305 | ⚠️ **Частично защищено / принятый риск**. Содержимое сообщений и файлов зашифровано E2E, но транспорт — открытый HTTP/WebSocket: пароль при входе, сессионные токены и метаданные (кто, кому, когда, размер) видны в сети. Публичный ключ собеседника выдаётся сервером без внешней верификации. Подробнее — раздел 4. |
| **Перебор пароля / кода привязки** | Ограничение частоты попыток входа и завершения привязки; константное время ответа | ✅ Защищено. 5 неудачных попыток для пары IP+логин или 30 с одного IP → `429 Too Many Requests` с `Retry-After`, экспоненциальная задержка 30 с … 15 мин. Для несуществующих пользователей выполняется фиктивная проверка bcrypt, чтобы по времени ответа нельзя было перечислять логины. Код привязки: 10 попыток, TTL 5 минут. |
| **Утечка сессионного токена** | Передача токена только в HTTP-заголовке (`Authorization: Bearer` / `X-Session-Token`), в БД хранится SHA-256 хэш; сессии живут 30 дней с продлением при активности; `POST /api/logout` | ✅ Защищено в рамках модели. Токен не попадает в URL (логи прокси/роутера, история), в БД нет значения, пригодного для входа. WebSocket проверяет совпадение `device_id` с сессией. |
| **Компрометация одного из устройств** | Механизм отзыва (`/api/devices/revoke`) | ✅ Защищено. Отзыв удаляет устройство из списка, аннулирует **все его сессии** и разрывает активное WebSocket-соединение. Отозванное устройство получает `403` на любой запрос и автоматически выполняет локальную полную очистку (ключи, токен, история). Ключевая пара пользователя при этом общая для всех его устройств — см. раздел 4, п. 3. |
| **Принуждение к разблокировке (Duress)** | Пароль принуждения (`duress_password`), запускающий скрытый вайп | ✅ Защищено. Ввод этого пароля с **любым** логином незаметно запускает стирание. Сравнение — за постоянное время, ответ сервера и его длительность неотличимы от обычной ошибки «неверный логин или пароль». Сервер отказывается стартовать с коротким (< 8 символов) или документационным значением пароля. |
| **Захват оставленного без присмотра сервера** | *Dead Man's Switch* (автовайп при отсутствии активности админа > `timeout_days`) | ✅ Защищено. Учитывается активность любого устройства администратора (вход, WebSocket, API). Первая проверка — через час после старта; скачки системных часов и явно неверное время (год < 2024) не приводят к ложному срабатыванию. Отключается через `dead_man_switch.enabled: false`. |
| **Форензика диска / SD-карты сервера** | SQLCipher (AES-256) + **полная** перезапись файла БД и WAL случайными байтами с `fsync`, затирание и удаление вложений | ✅ Защищено в рамках возможностей ПО. Полная перезапись выбрана потому, что БД открывается raw-ключом с USB: затирания одного заголовка было бы недостаточно для обладателя ключа. Ограничения flash-памяти — раздел 2.1. |
| **Форензика диска / памяти клиента** | Приватные ключи и токен сессии — в secure storage (Android Keystore / Windows DPAPI); на Android приложение исключено из резервных копий и переноса данных (`allowBackup=false`, `dataExtractionRules`) | ⚠️ **Частично защищено**. Локальная SQLite-база клиента не шифруется: тексты сообщений хранятся в зашифрованном виде, но метаданные (время, собеседник, статус) — в открытом. Экран блокировки по биометрии/PIN работает по принципу fail-closed (при ошибке аутентификации приложение остаётся заблокированным). |
| **Вредоносный контент от собеседника** | Валидация имён файлов (только базовое имя, запрещённые символы заменяются), лимиты размера сообщения (64 КБ) и файла (`max_file_size_mb`) | ✅ Защищено. Имя файла из зашифрованных метаданных не может указывать на путь вне временной директории. |
| **Повреждение/подмена зашифрованного трафика** | AEAD (Poly1305) обнаруживает любое изменение шифртекста; клиент отказывается отправлять сообщение без ключа собеседника и помечает входящий открытый текст маркером `⚠️ [незашифровано]` | ✅ Защищено. |
| **Рассинхронизация часов в LAN** | Алгоритм *Time Delta Sync* (работает без NTP и батарейки RTC) | ✅ Защищено. |

## 2. Архитектура экстренного уничтожения данных (Panic / Duress Wipe)

Сервер HomeLAN рассчитан на сценарии, когда физическое оборудование (Orange Pi Zero 3 или диск) может попасть в чужие руки. Модуль `internal/panic/panic.go` выполняет затирание базы данных и файлов. Повторные вызовы из разных источников безопасны: процедура выполняется ровно один раз (`sync.Once`).

```
      [ Триггеры ]
 ├── Выдернута USB-флешка (USB Master Key)
 ├── Введен пароль принуждения (Duress Password)  ──► [ Модуль PanicHandler ]
 ├── Сработал таймер Dead Man's Switch                           │
 └── POST /api/panic (только админ, confirm=DESTROY_ALL_DATA)    │
                                                                 ▼
                                                  1. Закрытие соединения с БД (снятие локов)
                                                  2. Полная перезапись WAL случайными байтами, удаление WAL/SHM
                                                  3. Полная перезапись файла БД случайными байтами + fsync
                                                  4. Затирание заголовков (4 КБ) и удаление всех вложений
                                                  5. Удаление файла БД
                                                  6. Сброс буферов файловой системы (sync)
                                                  7. Завершение процесса (os.Exit)
```

### 2.1. Ограничения затирания на Flash-памяти (Wear Leveling)
При перезаписи файлов на современных Flash-накопителях (SSD, SD-карты, eMMC) контроллер накопителя использует алгоритм **выравнивания износа (Wear Leveling)**.

Это означает, что при перезаписи файла новые случайные байты могут быть записаны в другие физические ячейки, а старые помечены как «неиспользуемые» для последующей очистки сборщиком мусора. В этот промежуток времени физические ячейки с оригинальными данными всё ещё могут быть считаны специализированным лабораторным оборудованием (форензика чипов).

**Выводы и рекомендации:**
1. Разработчики не гарантируют 100% физическое затирание секторов на полупроводниковых дисках силами пользовательского приложения.
2. Для абсолютной защиты от лабораторного анализа аппаратной памяти сервера настоятельно рекомендуется использовать полнодисковое шифрование на уровне операционной системы (например, **dm-crypt / LUKS** в Linux) в сочетании со встроенным механизмом вайпа.

## 3. Сценарии активации защиты

### 3.1. Аппаратный ключ (USB Master Key)
* Сервер запускает фоновую горутину, которая проверяет наличие файла `homelan.key` на подключенных USB-накопителях каждую секунду.
* Для защиты от случайных скачков напряжения или кратковременных сбоев шины питания (glitch) система выполняет 3 быстрых повторных опроса (через каждые 50 мс) перед активацией экстренного удаления.
* Если диск действительно извлечен, сервер немедленно вызывает `Trigger("USB_KEY_GONE_CONFIRMED")`.
* Создание ключа (`--init-usb`) требует явного указания накопителя (`--usb <путь>`), если найдено больше одного кандидата — ключ не будет записан на случайный диск.

### 3.2. Пароль принуждения (Duress Password)
* В конфигурации `config.yaml` задается параметр `duress_password` (минимум 8 символов, не из примеров документации).
* Если пользователь под давлением вводит этот пароль на экране входа (имя пользователя может быть любым), эндпоинт `/api/login` возвращает обычную ошибку входа `401 Unauthorized` с тем же текстом и той же задержкой, что и при неверном пароле.
* В фоновом потоке через 500 миллисекунд активируется процедура полного уничтожения данных.

### 3.3. Переключатель мертвеца (Dead Man's Switch)
* Сервер раз в час проверяет время последней активности администратора по **всем** его устройствам (вход, WebSocket-соединение, обращения к API).
* Если с момента последней активности прошло более `timeout_days` (по умолчанию 30 дней), запускается автовайп.
* Защита от ложных срабатываний: проверка пропускается при явно неверном системном времени (год < 2024) и при резком скачке часов вперёд между проверками (Orange Pi Zero 3 без батарейки RTC, ручная установка даты). Первая проверка выполняется через час после старта процесса.

### 3.4. Отзыв устройства
* Любой пользователь может отозвать своё устройство в **Настройки → Устройства**.
* Сервер удаляет устройство, помечает все его сессии отозванными и закрывает WebSocket. Отозванное устройство при следующем обращении получает `403 Device revoked` и выполняет локальную полную очистку. Повторная регистрация того же `device_id` невозможна (`409 Conflict`) — требуется новая привязка с нового идентификатора.

## 4. Криптографические ограничения (принятые риски)

1. **Открытый транспорт (HTTP / ws://):**
   Пароль при входе, сессионные токены и метаданные передаются без TLS. В закрытой домашней сети без посторонних устройств это принято как допустимый риск. При необходимости сервер можно поставить за обратный прокси с TLS (nginx/caddy) — клиент поддерживает `https://`-адреса и проверяет сертификаты штатно (отключение проверки сертификатов убрано).

2. **Отсутствие Perfect Forward Secrecy (PFS):**
   В протоколе E2E используются статические ключи **X25519** для деривации общего секрета. Если злоумышленник скомпрометирует приватный ключ одного из пользователей, он сможет расшифровать всю историю переписки (включая перехваченные ранее сообщения). PFS в текущей версии **не обеспечивается**.

3. **Одна ключевая пара на пользователя:**
   Все устройства пользователя разделяют одну пару X25519 (она передаётся при привязке через QR-код / текст «код + ключ»). Поэтому отзыв устройства не меняет ключ: если скомпрометированное устройство успело скопировать приватный ключ, его нужно считать раскрытым. Ротация ключей пока не автоматизирована — при подозрении на компрометацию выполните «Полную очистку» на всех устройствах и зарегистрируйтесь заново.

4. **Доверие серверу в части публичных ключей:**
   Публичный ключ собеседника клиент получает от сервера и кеширует локально. Внеполосная верификация отпечатков (safety numbers) не реализована; клиент не допускает отправку без ключа и явно помечает входящие незашифрованные сообщения.

5. **ChaCha20-Poly1305 vs XChaCha20-Poly1305:**
   Код использует стандартный **ChaCha20-Poly1305** с 12-байтовым случайным nonce, генерируемым при каждом шифровании. Во избежание риска повторного использования пары (key, nonce) разработчики рекомендуют периодически обновлять ключевую пару пользователей.
